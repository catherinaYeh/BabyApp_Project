# Feature Specification: Supabase 資料庫遷移

**Feature Branch**: `feature/supabase-migration`

**Created**: 2026-06-20

**Status**: Draft

**Input**: User description: "將副食品紀錄 App 從 LocalStorage 遷移到 Supabase。需求包含：(1) 建立對應 Supabase 的資料表關聯設計 (Baby, FoodItem, FeedingRecord)。(2) 將原本前端的 storageService（或相關的 LocalStorage 讀寫邏輯）替換為呼叫 Supabase SDK 的非同步方法。(3) 處理讀取資料時的 Loading 狀態與 Error 處理。"

> **重要前提澄清（與原始需求對照）**
> 經檢視現有程式碼，本 App 的副食品資料 **目前並非存放在 LocalStorage**，而是已透過後端服務（NestJS + Prisma）持久化於 PostgreSQL，前端透過 REST API 存取；LocalStorage 僅用於 UI 狀態（目前選取的寶寶、佈景主題）。因此本規格在使用者確認後，將「遷移到 Supabase」定義為：
>
> - **方向**：保留現有後端與前端資料存取層，將後端的資料庫改為 **Supabase 託管的 PostgreSQL**。
> - **認證**：不納入使用者登入，維持單租戶（單一共用資料集）。
>
> 原始需求的三點在此前提下對應為：(1) 確保 Baby / FoodItem / FeedingRecord 三張資料表與關聯正確建立於 Supabase；(2) 既有資料存取層改以 Supabase 託管資料庫為後端，維持非同步存取且不更動 UI；(3) 確保資料載入中的 Loading 狀態與連線/錯誤情境有清楚回饋。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 副食品資料持久保存於雲端資料庫 (Priority: P1)

身為照顧者，我希望我為寶寶記錄的每一筆副食品嘗試（吃了什麼食物、時間、份量、過敏反應）都被可靠地保存在雲端託管的資料庫中，讓資料不會因為單一伺服器或本機環境問題而遺失，並能在重新開啟 App 後完整呈現。

**Why this priority**: 這是整個遷移的核心價值——資料的可靠保存。若沒有這項，其他狀態回饋都無意義。完成這一項即構成可交付的 MVP：資料正確地落在 Supabase 並能讀回。

**Independent Test**: 將後端指向 Supabase 後，透過 App 新增一筆餵食紀錄，於 Supabase 後台確認該筆資料存在於對應資料表；重新整理 App 後該筆資料仍正確顯示。

**Acceptance Scenarios**:

1. **Given** 後端已連線至 Supabase 託管資料庫且資料表已建立, **When** 使用者新增一筆餵食紀錄, **Then** 該紀錄被寫入 Supabase 並在列表中立即可見。
2. **Given** App 中已有先前記錄的資料, **When** 使用者關閉並重新開啟 App, **Then** 所有先前的寶寶、食物與餵食紀錄皆完整載回，無資料遺失。
3. **Given** 使用者刪除一隻寶寶, **When** 操作完成, **Then** 該寶寶關聯的餵食紀錄一併被移除，且系統食物清單不受影響（維持既有關聯規則）。

---

### User Story 2 - 資料載入時的清楚進度回饋 (Priority: P2)

身為使用者，當 App 正在從雲端資料庫讀取資料（例如開啟歷史紀錄或切換寶寶）時，我希望看到明確的載入中提示，而不是空白畫面或畫面凍結，讓我知道系統正在運作。

**Why this priority**: 雲端讀取相較本機存取有網路延遲，缺乏載入回饋會讓使用者誤以為當機。屬於體驗保障，建立在 P1 之上。

**Independent Test**: 在受限網路（人為增加延遲）下開啟需要讀取資料的頁面，確認載入期間顯示載入指示，資料抵達後正確替換為內容。

**Acceptance Scenarios**:

1. **Given** 使用者開啟需從雲端讀取資料的頁面, **When** 資料尚在傳輸中, **Then** 畫面顯示載入指示（例如載入動畫／骨架畫面），不顯示空白或殘缺內容。
2. **Given** 資料已成功讀取, **When** 載入完成, **Then** 載入指示消失並顯示實際資料。
3. **Given** 查詢結果為空（例如新寶寶尚無紀錄）, **When** 載入完成, **Then** 顯示清楚的「尚無資料」空狀態，而非持續載入。

---

### User Story 3 - 連線或讀寫失敗時的友善錯誤處理 (Priority: P3)

身為使用者，當 App 無法連上雲端資料庫或讀寫失敗時，我希望看到清楚、友善的錯誤訊息，並能再次嘗試，而不是看到技術性錯誤或畫面卡死。

**Why this priority**: 雲端後端引入了新的失敗面（網路、資料庫不可用）。良好的錯誤處理可避免使用者困惑與資料誤判，但屬於可靠性強化，優先序低於核心保存與載入回饋。

**Independent Test**: 模擬資料庫不可用或請求失敗，確認 App 顯示友善錯誤訊息並提供重試，恢復連線後重試可成功載入。

**Acceptance Scenarios**:

1. **Given** 雲端資料庫暫時不可用, **When** 使用者嘗試讀取資料, **Then** 顯示友善錯誤訊息與重試選項，而非技術堆疊或空白畫面。
2. **Given** 寫入操作失敗（例如新增紀錄時連線中斷）, **When** 失敗發生, **Then** 系統告知使用者操作未成功，且不會在畫面上留下看似已成功的假資料。
3. **Given** 先前發生讀取錯誤, **When** 使用者點選重試且連線已恢復, **Then** 資料成功載入並回到正常狀態。

---

### Edge Cases

- **既有資料搬移**：遷移前若已有資料存在於原資料庫，搬移到 Supabase 後筆數與內容需一致，不可遺漏或重複。
- **系統預設食物**：系統內建食物清單（is_system）需在新資料庫中存在，否則餵食紀錄無可關聯的食物。
- **唯一性衝突**：同一寶寶在同一時間對同一食物的重複紀錄，需維持既有的唯一性限制，避免重複寫入。
- **關聯完整性**：刪除寶寶時其餵食紀錄應一併刪除；食物若仍被紀錄引用則不可被刪除（維持既有刪除規則）。
- **連線中斷於寫入途中**：寫入過程中連線中斷時，不可造成部分寫入或畫面顯示假成功。
- **冷啟動延遲**：託管資料庫於閒置後首次連線可能較慢，載入回饋需涵蓋此情境而非逾時當機。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系統 MUST 在 Supabase 託管的資料庫中建立 Baby、FoodItem、FeedingRecord 三張資料表及其關聯（寶寶與餵食紀錄為一對多；食物與餵食紀錄為一對多），並保留既有欄位、預設值與關聯規則。
- **FR-002**: 系統 MUST 保留並建立既有的資料完整性規則：刪除寶寶時連帶刪除其餵食紀錄；食物若仍被餵食紀錄引用則不可刪除；同一寶寶／食物／餵食時間的組合維持唯一性。
- **FR-003**: 系統 MUST 將既有資料（若有）完整搬移至 Supabase，遷移後資料筆數與內容與來源一致。
- **FR-004**: 系統 MUST 在新資料庫中具備系統預設食物清單，使餵食紀錄可正確關聯到食物。
- **FR-005**: 應用程式的所有副食品領域資料（寶寶、食物、餵食紀錄）讀寫 MUST 以 Supabase 託管資料庫為唯一真實來源；領域資料 MUST NOT 再依賴 LocalStorage 作為持久化儲存。
- **FR-006**: 資料存取邏輯 MUST 維持封裝於獨立的服務／資料存取層，前端 UI 元件不直接耦合資料來源（符合專案憲章：前後端解耦）。
- **FR-007**: 遷移 MUST NOT 改變現有 UI 元件的外觀與使用者操作流程（符合專案憲章）。
- **FR-008**: 資料讀寫操作 MUST 以非同步方式進行，且在資料抵達前提供載入中狀態，不顯示空白或殘缺畫面。
- **FR-009**: 當查詢結果為空時，系統 MUST 顯示明確的空狀態，而非持續顯示載入中。
- **FR-010**: 當讀取或寫入失敗（含資料庫不可用、網路錯誤）時，系統 MUST 顯示友善的錯誤訊息並提供重試方式。
- **FR-011**: 寫入失敗時，系統 MUST 不在畫面上保留看似成功的資料，並讓使用者知悉操作未完成。
- **FR-012**: 資料庫連線設定（指向 Supabase 的連線資訊與憑證）MUST 以環境設定方式管理，不可硬編於程式碼，並能於各部署環境（本機／後端託管平台）正確套用。

### Key Entities _(include if feature involves data)_

- **Baby（寶寶）**：代表一位被記錄的嬰幼兒。關鍵屬性：名稱、出生日期、頭像顏色、建立／更新時間。與 FeedingRecord 為一對多關聯（一隻寶寶有多筆餵食紀錄）。
- **FoodItem（食物項目）**：代表一種副食品食材。關鍵屬性：名稱（唯一）、分類、過敏風險等級、是否為系統內建。與 FeedingRecord 為一對多關聯（一種食物可出現在多筆餵食紀錄）。
- **FeedingRecord（餵食紀錄）**：代表一次餵食嘗試。關鍵屬性：所屬寶寶、所餵食物、餵食時間、份量、嘗試次數、反應、備註、建立時間。關聯：屬於一隻寶寶與一種食物；同寶寶／食物／時間維持唯一。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 遷移完成後，App 中新增的每一筆餵食紀錄皆能在 Supabase 後台被查到，且 App 重啟後 100% 完整載回，無資料遺失。
- **SC-002**: 既有資料搬移後，來源與 Supabase 中三類實體的資料筆數一致（差異為 0）。
- **SC-003**: 所有需從雲端讀取資料的畫面，在資料抵達前 100% 顯示載入回饋，不出現空白或殘缺畫面。
- **SC-004**: 在資料庫不可用的模擬情境下，使用者 100% 看到友善錯誤訊息與可用的重試，且恢復後重試可成功載入。
- **SC-005**: 遷移前後，使用者完成「新增一筆餵食紀錄」的操作步驟與畫面外觀維持不變（UI 無回歸）。
- **SC-006**: 一般網路情況下，主要資料畫面（首頁、歷史紀錄）自開啟到顯示資料的時間在 3 秒內完成。

## Assumptions

- 採用「保留現有後端、將資料庫改為 Supabase 託管 PostgreSQL」的方向；不改以前端直連資料庫，亦不移除現有後端（依使用者確認）。
- 本次遷移不納入使用者登入與多租戶隔離，維持單一共用資料集（依使用者確認）；未來若需多使用者，將另立規格。
- 既有 Baby / FoodItem / FeedingRecord 的資料模型與關聯設計沿用現況，遷移以「相同結構落地於 Supabase」為原則，不在本次變更資料模型語意。
- 領域資料原本即不存放於 LocalStorage；LocalStorage 僅承載 UI 狀態（選取寶寶、佈景主題），不在本次遷移範圍內。
- 既有前端已具備非同步資料讀取與基本載入／錯誤處理機制，本次以「確保其在 Supabase 後端下正確運作並補齊缺口」為目標，而非重寫資料層。
- 使用者具備可正常連線網際網路的環境；離線使用不在本次範圍。
- 具備可用的 Supabase 專案與連線憑證，並可於後端託管平台設定對應環境變數。
